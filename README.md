# Project Delivery Analyst

版本：`v1.3.0`

`project-delivery-analyst` 是一个面向 Codex / AI 编程助手的通用任务路由 Skill。它不只处理项目交付，还负责先判断任务该走哪条路，再按需进入产品原型与交互需求文档、需求梳理、项目理解、技术设计、数据库设计、接口落地、AI 工作流约束、仓库规则工作流包、开发门禁、任务追溯、发布准备和合规校验。

它适合用于 0-1 项目启动、二次开发项目接手、功能修复、逻辑修复、交付文档生成、上线前纠偏，以及给 AI 编程助手生成项目级约束规则。若任务本身不是交付类，它会优先做分流和最小必要检查，而不是强行套完整流程。

- 新增 OpenSpec / Loops 引用，用于把 AI 开发拆成可控阶段，避免无限扫描和无限重试。
- 新增产品原型与交互需求文档模块，支持作为页面型项目的前置第一产物，也支持单独生成。
- 将入口 `SKILL.md` 升级为主控路由器，需要哪个能力就按需读取对应 reference。

## 核心定位

这个 Skill 扮演的是“通用任务路由器 + 项目经理 + 架构师 + 开发门禁 + 交付审查”的组合角色：

- 项目经理：把模糊想法、口头需求、工单、PRD、竞品材料整理成明确范围。
- 架构师：把功能拆到页面、接口、服务、数据库、状态流转和异常处理。
- 开发门禁：限制 AI 只做当前批次，不跨范围扫描和修改。
- 交付审查：检查文档、代码、测试、发布和风险是否闭环。

它的目标不是替代人工确认，而是让 AI 在进入实现前先把范围、证据、链路和验收标准讲清楚。默认后端实现语言按 Go 处理，除非仓库或用户明确给出其他语言。

## 三层运行架构

### 1. 入口层

先判断任务类型：问答、排障、写文档、改代码、做计划、做评审、发版、复盘。入口层只负责分流，不会把低风险任务强行套进 PRD、批次门禁或链路契约。

### 2. 通用层

保留所有任务都需要的基本约束：先看上下文、先给结论、不确定就标 `待确认` 或 `仍未闭环`、只改相关范围、用证据说话。

### 3. 专长层

只有任务真的需要时才加载对应模块，例如 PRD、数据库、接口、发布、任务追踪、OpenSpec / Loops、仓库规则工作流包、开发修复门禁。

## 能做什么

### 1. 需求梳理与 PRD

适用于“我有个想法”“帮我写需求”“帮我出 PRD”“从 0 到 1 梳理项目”这类任务。

它会先识别业务背景、用户角色、核心流程、范围与非目标、验收标准、风险和待确认事项。需求还不清楚时，会先追问，不会直接编造完整方案。

可产出：

- `PRD.draft.md` / `PRD.md`
- 需求摘要
- 角色与权限说明
- 正常流程与异常流程
- 验收标准
- 待确认问题清单

### 0. 产品原型与交互需求文档

适用于不管是 0-1 项目还是二次开发项目，都必须先产出《XX(名称)-X端-APP/小程序/H5/... 产品原型 & 交互需求文档》的场景。它既可以作为页面型项目的前置第一产物，也可以单独作为最终产物。

它会先把页面、交互、跳转、异常、全局规则和原型说明钉住，再作为后续模块分析、功能拆解和接口设计的输入。

可产出：

- `prototype-interaction-doc.md`
- `XX(名称)-X端-APP/小程序/H5-产品原型&交互需求文档.md`
- 项目概述
- 整体业务流程图
- 页面原型总览
- 分页面详细需求
- 全局通用规则
- 非功能要求
- 附录

### 2. 二次开发项目理解

适用于接手已有项目、分析 README / 代码仓库、判断能复用什么、准备二开改造。

它会按最小必要范围只读检查项目结构、关键模块、前后端入口、接口、模型、配置和文档，输出项目画像和复用建议。读到的结论必须带证据标签，未验证的内容不会冒充已确认。

可产出：

- `project-understanding.md`
- 项目画像
- 技术栈和模块关系
- 可复用资源清单
- 目标差异分析
- 风险和仍未闭环事项

### 3. 前后端闭环设计

适用于“这个按钮点了要走哪个接口”“这个页面和后端怎么闭环”“帮我设计接口落地链路”。

它会把一条功能链路拆清楚：前端入口、前端 API 封装、后端路由、请求 DTO、响应 DTO、业务服务方法、数据库影响、状态流转、事务、幂等、防重和异常处理。

可产出：

- `frontend-layout.md`
- `frontend-backend-closed-loop.md`
- `interface-implementation-guide.md`
- 接口契约表
- 前后端字段一致性检查
- 状态流转说明

### 4. 技术方案与数据库设计

适用于“出技术方案”“设计数据库”“评估表结构变更”“二开时字段怎么加”。

它会区分文档已确认、代码已存在、仍需人工确认的信息。数据库设计强调证据驱动，不会只凭功能名直接造表、造字段、造索引。

可产出：

- `tech-plan.md`
- `database.md`
- ER 图或表结构说明
- 字段、索引、约束、迁移和回滚策略
- 二开兼容性说明
- 数据风险和待确认项

### 5. 开发 / 修复门禁

适用于“修一个 bug”“补一个功能”“逻辑不对帮我改”“页面按钮没反应”等强执行任务。

它会先建立当前批次，不允许直接上来就改代码。进入实现前需要明确：

- 当前批次
- 允许修改范围
- 禁止修改范围
- 本轮核心验收标准
- 前后端 / 数据链路契约
- 本次影响文件清单
- 根因或实现计划
- 用户确认

可产出：

- 批次门禁表
- 影响文件清单
- 根因分析
- 实现计划
- 自测命令和结果
- 非本批次问题登记

### 6. AI 工作流与项目规则生成

适用于“给项目生成 AI 规则”“约束 AI 不要乱改”“建立研发闭环”“把 AI 工作流接进项目”。

它会把项目约束整理成可落地规则，重点控制 AI 的读取范围、修改范围、批次隔离、已验证逻辑保护、前后端链路校验、数据库变更、状态流转、测试验收和发布纠偏。

可产出：

- `project-ai-constraints.md`
- `.dev-rules/rule/` 规则草案
- AGENTS / AI rules 参考内容
- 批次隔离规则
- 开发前门禁
- 验收材料模板

### 7. OpenSpec / Loops 有界执行

适用于希望 AI 按阶段执行，而不是无限扫描、无限排查、无限重试的场景。

它会把变更拆成短契约：

- `proposal.md`：目标、范围、非目标、风险
- `spec.md`：验收标准、接口和数据契约
- `design.md`：实现边界、可靠性、安全、回滚
- `tasks.md`：阶段任务
- `summary.md`：最近摘要

Loops 思路用于控制执行：每轮只读当前阶段和短摘要，失败就记录命令、退出码和下一步，不自动 push、merge 或 release。

可产出：

- OpenSpec 变更目录结构建议
- Loops 阶段提示
- 有界执行规则
- 阶段性摘要
- 阻塞和失败记录

### 8. 任务追溯与发布准备

适用于交付收尾、上线前检查、需要给团队或答辩材料说明“做了什么、怎么验、还有什么风险”。

它会把任务目标、批次范围、解决方案、链路闭环、测试命令、验证结果、未覆盖风险和后续问题记录下来。

可产出：

- `docs/task-trace/README.md`
- `docs/task-trace/YYYY-MM-DD/task-001-name.md`
- `release-checklist.md`
- release notes
- 未覆盖风险说明
- 后续待处理问题清单

### 9. 合规校验与交付审查

适用于“检查这份文档合不合格”“校验技术评审”“上线前帮我纠偏”。

它会检查文档是否缺少关键章节、是否有 unsupported claims、是否混淆业务和技术内容、是否缺少证据、测试和追溯关系。

可产出：

- `compliance-report.md`
- `review-1.md`
- `review-2.md`
- 问题清单
- 修复建议
- 仍未闭环事项

### 10. 仓库规则工作流包

适用于“给项目生成 AGENTS.md”“把 AI 研发规则落到仓库”“生成 aiDoc / workflow 目录”“建立 REQ / BUG / CHORE 工作项闭环”这类任务。

它会把 AI 协作规则拆成仓库内可追溯材料，让项目不只靠聊天记录维持上下文。

可产出：

- `AGENTS.md`
- `aiDoc/README.md`
- `aiDoc/relations/`
- `aiDoc/modules/`
- `aiDoc/frontend-backend/`
- `aiDoc/examples/`
- `aiDoc/memory/`
- `workflow/README.md`
- `workflow/standards/`
- `workflow/work-items/active/<WORK-ID>.md`
- `workflow/openspec/changes/<WORK-ID>/proposal.md`
- `workflow/openspec/changes/<WORK-ID>/spec.md`
- `workflow/openspec/changes/<WORK-ID>/design.md`
- `workflow/openspec/changes/<WORK-ID>/tasks.md`
- `workflow/openspec/changes/<WORK-ID>/summary.md`
- `workflow/test-reports/`
- `workflow/release-plans/`
- `workflow/learnings/`
- `workflow/waivers/`

## 内置工作流

### 轻流程：讨论或单文档输出

适用于只问思路、只写 PRD、只写方案、只做文档校验的场景。

```text
用户输入
-> 判断任务类型
-> 必要时追问
-> 生成指定文档
-> 自检是否缺少证据和待确认项
```

效果：避免小任务被扩展成全链路工程任务。

### 中流程：只读项目理解

适用于二次开发项目分析、仓库画像、接手项目前的理解。

```text
限定读取范围
-> 只读检查文档和关键文件
-> 输出项目画像
-> 标记文档已确认 / 代码已存在 / 仍未闭环
-> 给出下一步建议
```

效果：先理解项目，再决定是否开发；避免直接重写已有能力。

### 强流程：开发或修复门禁

适用于任何代码修改、功能修复、逻辑修复或高风险改动。

```text
声明当前批次
-> 输出执行门禁表
-> 输出链路契约清单
-> 锁定影响文件
-> 给出根因或实现计划
-> 等待确认
-> 实施
-> 自测
-> 输出验收材料和后续问题登记
```

效果：防止 AI 扫到什么改什么，防止跨批次修复，防止只改前端假效果。

### 仓库原生工作项闭环

适用于希望把研发过程落在仓库文档中的团队。

```text
REQ / BUG / CHORE 工作项
-> PRD 或评审
-> 技术设计
-> OpenSpec 变更契约
-> 实现与测试
-> 提测记录
-> 发布计划
-> 经验沉淀
```

效果：聊天记录不再是唯一证据，后续接手的人可以从仓库文档追溯来龙去脉。

### 仓库规则工作流包生成流

适用于要把 AI 协作规则一次性沉淀进仓库的项目。

```text
确认项目类型和默认语言
-> 生成 AGENTS.md
-> 生成 aiDoc 上下文层
-> 生成 workflow 研发闭环层
-> 生成工作项和 OpenSpec 模板
-> 生成测试、发布、经验和豁免目录
-> 输出落地说明和后续维护规则
```

效果：把 AI 读什么、改什么、怎么验、怎么发布、怎么复盘全部放进仓库文件。

### OpenSpec / Loops 有界执行流

适用于 AI 多轮开发、复杂修复和长上下文任务。

```text
proposal
-> spec
-> design
-> tasks
-> summary
-> bounded loop
-> 阶段验证
-> 人工审查
```

效果：把 AI 的执行限制在当前阶段，减少上下文膨胀和无边界自动化。

## 使用后有什么效果

- 范围更清楚：每次任务先定当前批次、允许范围和禁止范围。
- 链路更完整：前端、接口、后端、数据库、状态和验收一起看。
- 证据更可靠：结论必须区分 `文档已确认`、`代码已存在`、`已测试通过`、`仍未闭环`。
- 交付更可追溯：PRD、设计、任务追溯、测试和发布材料可以互相对应。
- 仓库规则更完整：可以生成 AGENTS、aiDoc、workflow、OpenSpec、测试报告、发布计划和经验沉淀骨架。
- 风险更可控：未测试、未联调、未确认的内容不会被包装成完成。
- 更适合二次开发：先识别已有能力和复用点，再决定最小改动。
- 更适合团队协作：后来者可以根据文档知道为什么这么做、怎么验证、还有什么风险。

## 不适合做什么

- 不会替用户凭空确认业务规则、第三方 API、生产配置或性能指标。
- 不会在没有确认范围的情况下自动修改代码。
- 不会把 mock、临时代码或未测试结果说成生产可用。
- 不会替代人工需求确认、代码审查和上线审批。

## 常见触发方式

你可以这样使用：

- “帮我梳理这个想法，写 PRD。”
- “先帮我出《XX-APP 产品原型 & 交互需求文档》。”
- “读取这个二次开发项目，先输出项目画像。”
- “这个按钮到后端接口怎么闭环，帮我写接口落地指导。”
- “给这个项目生成 AI 约束规则，禁止 AI 乱改。”
- “给这个项目生成 AGENTS.md、aiDoc 和 workflow 规则包。”
- “按批次修复这个 bug，先输出门禁表和链路契约。”
- “把这次改动整理成任务追溯和发布说明。”
- “检查这份技术评审有没有缺项。”

## 校验

运行内置结构校验：

```bash
python scripts/validate_project_delivery.py --skill-root .
```

运行单元测试：

```bash
python -m unittest discover -s tests
```

校验脚本只做结构筛查。正式发布或交付前，仍需要人工做语义复核。
